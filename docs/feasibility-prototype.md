# Running the feasibility prototype

Status: experimental finite-run prototype. It records visible pixels, indexes original-image OCR, searches locally, and opens recorded moments in a native Qt timeline viewer. Saved personal trials can continue indexing in the background; no recording or login service is installed automatically. The low-level examples below differ from the recommended personal-trial profile, which selects deferred adaptive indexing.

For a guided session on your own monitor with resource logging, use the [personal trial instructions](personal-trial.md).

## Try the synthetic recall demo

From a terminal:

```bash
cd ~/code/omarchy-replay
./scripts/replay build
./scripts/replay demo --dir runs/try-001 --codec h264-vaapi
./scripts/replay view --dir runs/try-001
```

Search `Patrick XYZ-1042`, `XYZ-1043`, `Omakase cedar`, or `Omakase juniper`. These are fictional screens generated by the program. The demo writes 16 observations, including exact duplicates, and finishes before the viewer opens. Choose a fresh directory for another recording; existing datasets are never overwritten.

Keyboard: Ctrl+F focuses search; Up/Down selects a match and previews it immediately; Left/Right moves through recorded moments; F5 refreshes. Escape first leaves a focused control or dismisses a panel, then closes from neutral viewer focus. Search text and result selection stay in place when navigating the timeline. The viewer refreshes every two seconds while preserving the selected moment. Fit and 100% controls change image viewing scale.

H.264 and HEVC VAAPI encoders passed bounded checks on the development hardware; that does not establish support on other machines. For machines without a working VAAPI encoder, `--codec webp` is the lossless image comparison and is the CLI's portable default. `h264` and `hevc` use bounded software encoder settings. Unsupported encoders fail explicitly.

Command-line recall works too:

```bash
./scripts/replay search --dir runs/try-001 'Patrick XYZ-1042'
./scripts/replay list --dir runs/try-001
./scripts/replay extract --dir runs/try-001 --id 1 --out runs/try-001-first.png
```

## Compare the OCR performance experiment

```bash
./scripts/replay demo --dir runs/incremental-try-001 \
  --codec h264-vaapi --ocr-mode incremental --workload editing
./scripts/replay view --dir runs/incremental-try-001
```

`--ocr-mode incremental` reuses recognized text in unchanged regions and rereads the band containing changed pixels. Large changes, resizing, uncertain text geometry, and periodic refresh use full-frame OCR. `--ocr-mode full` remains the default and comparison baseline. `--workload editing` alternates one invoice digit in two places on an otherwise unchanged synthetic screen; the default `mixed` workload switches through the original scenes.

Optional `--ocr-cpu-percent 20` cooperatively spreads OCR work across time. Zero (the default) disables pacing. This is a target for the recorder's OCR work, not a strict whole-process CPU cap: layout analysis can run between callbacks, and capture, encoding, and compositor work are outside that budget. Lower values increase indexing delay and can cause missed sampling slots. Run statistics report sleeps, callback gaps, missed slots, and canceled observations. Each recognition pass has a ten-second deadline checked by callbacks; expiry stops recording with an error rather than indexing partial text. A partial pass that falls back to a full pass gets a fresh deadline. User cancellation discards the current unindexed observation and finalizes previously accepted video.

## Try capture with deferred indexing

```bash
./scripts/replay demo --dir runs/deferred-try-001 --codec h264-vaapi \
  --realtime --interval 2 --indexing deferred --ocr-mode incremental \
  --ocr-cpu-percent 5 --pending-frames 16 --pending-mib 64 --drain-seconds 0
./scripts/replay status --dir runs/deferred-try-001
./scripts/replay view --dir runs/deferred-try-001
```

This option starts a separate OCR worker. Capture keeps a bounded set of lossless originals on disk so the worker can recognize the exact captured pixels. Pending moments can be viewed immediately; text search covers only completed indexing. The viewer distinguishes pending, failed, disabled, and ready text. Blank recognized images are ready; old datasets with unknown OCR status are labeled separately.

`--drain-seconds` defaults to 10: after capture finishes, the command allows the worker that long to catch up, then stops it. Zero returns after capture/finalization and cooperative worker shutdown. Any unfinished recognition remains pending and can be resumed:

```bash
./scripts/replay index --dir runs/deferred-try-001 --ocr-mode incremental
./scripts/replay status --dir runs/deferred-try-001
./scripts/replay search --dir runs/deferred-try-001 'Patrick XYZ-1042'
```

Add `--ocr-cpu-percent 5` to pace this standalone worker too. A restarted worker begins with full OCR to rebuild its cache. Only one index worker can own a dataset. Ctrl+C preserves pending work; a corrupt source or recognition deadline becomes an explicit failed item with its original retained. Failed items are not retried automatically in this prototype.

The default backlog is at most 16 held originals and 64 MiB of compressed source data. Originals waiting for video finalization, failed originals, and staging orphans count toward those limits too. Reaching a backlog limit skips new distinct captures and increments `backlog_skipped_samples`; it preserves accepted history. Exact consecutive duplicates can still add observation timestamps without another source. A full queue can force a short video segment to close so indexed originals can be released. The dataset disk allowance must leave room for this backlog plus archive/index overhead.

Deferred indexing is experimental and **opt-in for the low-level CLI**; the personal-trial helper already selects it. Separating the processes adds memory, and video capture adds temporary WebP compression and disk writes. It absorbs temporary delays; it cannot sustain a capture rate permanently faster than indexing. Compare coverage, pending work, CPU, memory, and I/O together.

### Adaptive worker and recall priorities

Add `--scheduler adaptive --pending-frames 0` to a deferred run to use active/idle/request OCR allowances and retain the source-byte bound without a source-count gate. The low-level adaptive CLI defaults to a 60-second OCR deadline, 10% active allowance, 40% idle allowance after 60 seconds, and at least 30% for requested work. Sustained CPU utilization plus pressure selects the explicit pressure allowance; missing signals retain the active allowance. These cooperative targets do not cap total process-tree CPU or RAM. The personal-trial helper uses a different evaluated profile: 40% active, 50% idle/requested, 10% under pressure and a separate requested 60% native worker ceiling. See [saved-history indexing](index-service.md) for policy and enforcement details.

The low-level `view --index-while-viewing` option owns an adaptive worker while the viewer is open unless a worker already owns the dataset. The higher-level `./scripts/replay` launcher instead ensures the independent indexing service for saved personal trials, respecting a saved pause or stop; closing that viewer does not end indexing. Selecting a pending image briefly requests it and nearby history; P requests explicitly and C requests two minutes of catch-up. The viewer labels work waiting for a worker and incomplete search coverage. A standalone `index --follow --scheduler adaptive` worker can also process durable requests; stop it with Ctrl+C. Priority ordering applies with either scheduler, while allowance changes require adaptive mode.

Experimental `--ocr-mode regions` compares narrower two-dimensional regions at original resolution. Its crops and full fallback share one frame deadline. See [adaptive indexing and regions](adaptive-indexing-and-regions.md) for correctness, performance findings, and remaining limits.

## Exercise actual Wayland capture with controlled content

```bash
python scripts/headless_capture_check.py \
  --dir runs/wayland-try-001 --codec h264-vaapi \
  --duration 12 --interval 2 --measure
./scripts/replay view --dir runs/wayland-try-001/dataset
```

The harness launches an isolated nested Hyprland, creates a private headless output, verifies output isolation, and shows the synthetic fixture there. It records that output, searches the result, and extracts an image. A nested window can briefly appear during startup; the harness disables it before testing. All test processes are stopped afterward. Host screen pixels are not captured by this harness.

`--backend grim` selects the process-per-snapshot baseline. `--capture-only` skips storage/OCR. `--no-ocr` isolates acquisition, duplicate detection, and encoding. `--fixture-interval 60` keeps the first synthetic screen static during a short test. The reported recorder process-tree memory excludes the fixture, nested compositor, and GPU allocations.

The harness also accepts `--ocr-mode`, `--ocr-cpu-percent`, `--workload`, `--indexing`, `--pending-frames`, `--pending-mib`, and `--drain-seconds`. For an editing comparison with one changed invoice per capture, use `--workload editing --fixture-interval 2 --interval 2`; a faster fixture can alternate back to the same image between samples. The `mixed` workload means different content on a single monitor, not multiple monitors.

## Finite recording of a selected desktop output

This is a manual prototype path. It captures visible content on the explicitly selected output, subject to compositor exclusions. Replay viewer exclusion requires the [explicit installer](personal-trial.md#excluding-the-viewer); configurable application exclusions, lock/suspend policy, retention, and multi-output scheduling are not implemented yet. The controlled harness above is the reproducible test path.

```bash
./scripts/replay outputs
# Replace OUTPUT_NAME with one of the listed output names:
./scripts/replay record --output OUTPUT_NAME --dir runs/manual-001 \
  --duration 30 --interval 2 --codec h264-vaapi
./scripts/replay view --dir runs/manual-001
```

Recording ends after the requested duration or Ctrl+C, with the current work unit and finalization time in addition. Recording/demo and indexing processes lower their CPU scheduling priority to nice 10, or preserve an already lower priority. The interval is adjustable from 0.25 to 60 seconds in this prototype; that is an input range, not a promise that every cadence can be sustained. Durations are bounded to four hours; this limit is not evidence of a completed four-hour reliability test. Missed schedule slots, backlog skips, and capture timeouts are reported separately in `run.json`. Default processing is synchronous; `--indexing deferred` separates capture from OCR using the bounded queue described above.

## Reproduce checks and measurements

```bash
REPLAY_TEST_VAAPI=1 ctest --test-dir build --output-on-failure
python scripts/benchmark.py --out runs/codec-check-001
python scripts/check_media.py runs/codec-check-001/h264-vaapi
python scripts/foreground_check.py --out runs/foreground-001 --pairs 3
```

The codec benchmark renders the same synthetic observations for each codec, measures recorder/encoder process memory, stores original-image OCR, and checks known search terms. It runs in a burst unless `--realtime` is supplied. `check_media.py` decodes retained frames and checks their text again; a small file alone is not a quality result. Measurements of fresh CLI extraction include process/decoder startup.

The foreground check alternates a short CPU-bound probe with and without a nice-10 synthetic recorder. `--same-cpu` constrains only those test processes to one allowed CPU. It does not measure browser interaction, video playback, compositor frame timing, or the impact of recording the user's actual desktop. Do not generalize its results to a smoothness guarantee.

## Implementation and limits

- C++20 with Qt6, Tesseract/Leptonica, OpenMP runtime control, SQLite FTS5, libwebp, libwayland-client, and FFmpeg/ffprobe. Builds use CMake, pkg-config, wayland-scanner, and installed Wayland protocol XML. These dependencies were already present on the development machine; the wrapper performs no package installation.
- The native capture client reuses its Wayland connection and SHM buffer. Each sample creates a fresh protocol session to obtain a first-frame capture without indefinitely waiting for damage. Calls and image dimensions are bounded; captured images own their pixels.
- Exact consecutive pixel hashes suppress redundant OCR/media, while individual observation timestamps remain in SQLite. Reappearance after different content creates another retained moment. A blinking caret or animation can still force more work.
- OCR uses original-resolution pixels and one warm English Tesseract engine. A scoped OpenMP runtime setting serializes recognition even when the executable is launched directly without environment settings. The default is full-frame OCR; incremental recognition and cooperative CPU pacing are experimental options. There are no embeddings, model calls, or periodic summaries.
- Video pixels stream directly to a bounded FFmpeg pipe. Deferred indexing additionally stores compressed lossless WebP originals in `staging/`; WebP archives reuse their original images. There is no temporary raw-frame or PNG spool. Segments have frame-count and real-time-span limits. Video timestamps and recorded observation times are separate; arbitrary-frame retrieval currently decodes from the segment start.
- A dataset uses `index.sqlite`, `media/`, and bounded run metadata. The default disk allowance is 512 MiB with a 256 MiB free-space reserve. Reaching limits stops recording rather than deleting history. New directories are private; generated data lives in ignored `runs/`.
- Completed video is exposed after encoder exit and frame-count verification. An interrupted unfinished segment remains marked unavailable; deferred datasets can still display its retained originals. There is no video repair or recording-resume implementation. Default synchronous recording uses SQLite WAL with NORMAL synchronization. Deferred datasets use FULL synchronization and flush originals before publishing their pending rows; originals are removed only after indexing and archive completion. These are process-recovery precautions, not tested power-failure guarantees. A hard kill can leave partial files or staging orphans.
- Adaptive idle/pressure scheduling, a keyboard timeline, and independent saved-history indexing are implemented. Requested OCR ceilings use transient systemd user services. There is no S3 transfer, automatic retention, installed recording/login service, or recording-resume implementation. These remain prototype components, not evidence of all-day reliability.

See the [measurement results](feasibility-results.md) for what passed and which performance goals remain unmet.
